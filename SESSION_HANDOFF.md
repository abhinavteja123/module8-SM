### New feature — Activity Monitor (CRCS Coordinator / HOD / Dean / School Office / Faculty Coordinator)

Built end-to-end per explicit request: a page to see whether faculty/students are actually using the portal (logins, faculty research postings, student applications), not just enrollment counts.

- **`users.last_login_at`** (migration 041) is stamped by `POST /login` on every successful sign-in, fire-and-forget so a failed write never blocks login. It only tracks logins *since this feature shipped* — anyone who logged in earlier legitimately shows no timestamp. The UI never says "Never logged in" for that reason; see below.
- **`GET /oversight/activity?cycle_id&person_type=faculty|student&page&search&department_id&login_status&pathway&activity`** (new route in `backend/src/routes/oversight.js`) returns paginated, scoped rows: faculty get last login, research projects posted (+latest date), active mentee count, last audit-logged action; students get last login, chosen pathway, application count (+latest date), last audit-logged action.
  - Scoping reuses `directoryPage` (the same primitive `admin/student-records` uses) for HOD (department), Dean/School Office (school, with a department-narrowing filter), and CRCS coordinator/superadmin (everything, filterable by department). **Faculty Coordinator is a special case, fixed this session:** it does *not* reuse the department-wide `directoryPage` scope — it's restricted server-side to only the specific faculty CRCS mapped to them via `faculty_coordinator_assignments`, plus those faculty's current mentees, matching how coordinator mapping actually works everywhere else in the app. A department filter is deliberately not offered to Faculty Coordinators in the UI since their scope is already narrower than a department.
  - `login_status` / `pathway` / `activity` filters can't be pushed into `directoryPage`'s SQL without a join it doesn't do, so when any of them is set the route does a bounded full-scope scan (capped at 2000 people, `ponytail:` comment names the ceiling and the upgrade path) before filtering+paginating in memory. Plain browsing (no extra filter) still uses the original fast single-page-at-a-time path.
- **`GET /oversight/activity/:personType/:id?cycle_id=`** — click-through detail endpoint: full application list (title/type/status/date) for a student, or full research-project list + current mentee list for faculty. Authorization is scope-checked per role the same way as the list endpoint (including the Faculty Coordinator special case).
- **`frontend/src/features/oversight/ActivityMonitorPage.jsx`** — new page, mounted at both `/coordinator/activity` and `/crcs/activity` (same component). Filters: search, department (role-gated), login status, pathway (student tab only), applications/activity level, with a Clear-filters button. Rows are clickable and open a detail modal via the endpoint above. Linked from `CoordinatorLayout.jsx` (hod/dean/school_office/faculty_coordinator) and `CRCSLayout.jsx` (gated on the existing `view_analytics` permission — no new CRCS-coordinator permission key was added, deliberately, to avoid the trap of a permission that can never be granted because it's missing from `CRCSPermissionsConfig.jsx`'s catalogue).

Fixed: the badge now reads "No login recorded", and when the same row already shows other proof of use, it adds "Active before login tracking began" instead of flatly implying the person never touched the portal.
